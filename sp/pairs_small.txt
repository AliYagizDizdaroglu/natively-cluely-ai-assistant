===== W01 [easy / Docker / spoken] =====
QUESTION: To start, what is the difference between a Docker image and a container?
ANSWER (41 words): An image is a read-only template that contains the application code, libraries, and dependencies needed to run a program. A container is a live, runnable instance of that image. If the image is the blueprint, the container is the actual building.

===== W02 [easy / Docker / spoken] =====
QUESTION: Why do Docker layers matter for build times?
ANSWER (63 words): Docker layers matter because they allow for caching; when you rebuild an image, Docker only re-runs the steps that have changed and reuses the cached layers for everything else. By ordering your Dockerfile from the least-frequently changed to the most-frequently changed instructions, you minimize the amount of work required for each build. This drastically reduces build times and speeds up the deployment pipeline.

===== W03 [easy / S3 / spoken] =====
QUESTION: When would you use S3 Standard versus S3 Glacier for training data?
ANSWER (71 words): I'd use S3 Standard for active training sets where the model needs frequent, low-latency access to the data during the training loop. S3 Glacier is for archival data or raw datasets that are rarely accessed and only need to be retrieved for periodic retraining or auditing. The choice comes down to the trade-off between the high cost of frequent access in Standard and the retrieval delays and costs associated with Glacier.

===== W05 [easy / Airflow / spoken] =====
QUESTION: What is a DAG, and why does Airflow use that structure?
ANSWER (67 words): A DAG, or Directed Acyclic Graph, is a collection of tasks organized in a way that defines their execution order and dependencies, ensuring the workflow only moves forward and never loops back on itself. Airflow uses this structure because it allows for complex dependency management, enabling tasks to run in parallel where possible while guaranteeing that a downstream task only starts once its prerequisites are successfully completed.

===== W06 [easy / CI/CD for ML / spoken] =====
QUESTION: Why version model artifacts alongside code?
ANSWER (63 words): Versioning model artifacts with code ensures that every prediction can be traced back to the exact dataset, hyperparameters, and code version used to produce it. This prevents "training-serving skew" where a model behaves differently in production because it was paired with a different version of the preprocessing logic. It essentially turns the model into a reproducible software asset rather than a black-box file.

===== W07 [easy / Kubernetes / spoken] =====
QUESTION: What is the difference between a pod and a deployment?
ANSWER (65 words): A pod is the smallest deployable unit in Kubernetes, representing a single instance of a running process. A deployment is a higher-level object that manages pods, allowing you to define the desired state—like how many replicas should run—and handling automatic scaling and rolling updates. Essentially, you rarely create pods directly; you use a deployment to ensure those pods are maintained and replaced if they fail.

===== W08 [easy / Monitoring/drift / spoken] =====
QUESTION: What is the difference between data drift and concept drift?
ANSWER (82 words): Data drift happens when the input data changes, meaning the distribution of the features you're feeding the model has shifted, even if the relationship between input and output remains the same. Concept drift is different because the actual relationship between the input and the target variable changes, meaning the "concept" the model learned is no longer true. Essentially, data drift is a change in what the model sees, while concept drift is a change in what the model is trying to predict.

===== W12 [easy / Airflow / spoken] =====
QUESTION: What is the difference between an Airflow operator and a sensor?
ANSWER (69 words): An operator defines a single task in a workflow, like executing a Python script or running a SQL query, to perform a specific action. A sensor is a special type of operator that polls for a specific condition to be met—like a file appearing in S3 or a record hitting a database—before allowing the downstream tasks to proceed. Essentially, operators do the work, while sensors wait for the trigger.
