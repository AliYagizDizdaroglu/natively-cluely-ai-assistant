## New findings

### N1 (Important): a tier with no captured ids crashes the real-data scorer, after grading has been paid for

Anchors: `flash-h40b-score-blind.mjs:71-80`, exposed by `flash-h40b-blind-pairs.mjs:51,62`.

- **Mechanism.** `totals[t]` is created only inside the per-id loop (`:73`). With `ids: []`, `const T = totals[t]` (`:78`) is `undefined`, and `T.acc` (`:80`) throws.
- **The crash hits the first empty tier in key order.** Tier 1 is first, so tiers 2, 3 and 3b and both lite totals never print.
- **Why the fix exposes it.** The code is unchanged from round 0, but round 0's builder exited 2 on the missing tier-1 files *before* anyone graded. The I2 fix correctly lets the builder through. The failure has therefore moved to after the Opus grading agents have run.
- **The claim it contradicts.** The implementer's report says of this exact case "nothing crashes"; that was checked on the builder only. The I2 ruling names "a tier with no captured ids", and the I3 ruling says the scorer is "non-fatal".
- **Scenario.**
  1. The h40b hour captures neither R02F nor R08 (or none of R03/R09F/R16, or prompts.json comes out empty).
  2. The sidecar writes `"1": { ids: [], skipped: [...] }`.
  3. Flight-day step (3): blind pairs exit 0, then Opus grades.
  4. `flash-h40b-score-blind.mjs` exits 1, and no tier's score is readable until the scorer is patched.
- **Likelihood: low.** h40a captured every tier id; its one uncaptured item, R09, is not a tier id.
- **Fix.** One line: initialise `totals[t]` before the id loop (or `?? {acc: 0, n: 0, ttft: [], thoughts: [], total: []}`). Add an empty-tier fixture case to the proof.

### N2 (Important): with one try, a cut whose re-ask returns 429/503 costs 2 requests, is charged 1, and loses the cut answer without trace

Anchors: `gemma-answers.mjs:335-341, 350-352`; `flash-h40b-sidecar.mjs:135-138`.

- **Mechanism.**
  - Call 1 is cut, so `dropRetried` is set and the loop continues.
  - Call 2, the re-ask, returns a transient 429 or 503. `attempts` = 2 ≥ 1, so the loop breaks.
  - The record takes the transient branch, `{ ...item, model, transientError }`, which has no `cutRetried`.
  - The sidecar charges `todo.length` plus `cutRetried` = 1. Two requests were made.
  - The first call's partial answer is overwritten and discarded. Nothing in the record shows that a cut or a first request happened.
- **Proven on the literal text.** In the one-try table above, these are the only 2 of 11 behaviours with charge < calls.
- **It contradicts:**
  - the ruling ("re-asked exactly once with cutRetried set (so the sidecar's `used += cutRetried` counts it)");
  - the report ("now counts a request that actually happens").
- **Why the harness missed it.** The case "re-ask comes back 429" (`i1-retry-trace.mjs:91`) is marked OK because it checks the loop variable `dropRetried`, not the stored record, which is what the sidecar reads. This is the rule-8 trap: the probe checked a proxy.
- **Scenario.**
  - The history makes it plausible on 3.8-flash: it cut 3 of 8 answers on 2026-09-11, and on 09-25 the full Flash models had 503 windows lasting minutes.
  - Take tier 1 `def`: R02F is cut after 2 minutes, then the re-ask gets a 503.
    - Real requests: 2. Charged: 1.
    - R02F returns to `todo` with no answer. The partial answer the round-0 code would have kept is gone.
  - Each such event lowers `used` below real, so the gate (`:132`) can admit one more pass than the 18 allows.
  - `tiers.json.requests`, which Task 5 Step 5 and `project_gemini_quota.md` will quote, under-reports by 1 per event.
  - The damage is bounded by the server's 20/day. It is silent.
- **Fix.** Write `cutRetried: dropRetried` on the transient record too (`:351`); the sidecar then counts it with no change of its own.
  - This also adds the field to default-4 transient records that followed a cut: one new field, no control-flow change.
  - Checked in memory (`<RR>/suggested-fix-check.mjs`): under-counted one-try behaviours go from 2 to 0.
  - Whether to keep the partial answer when the re-ask fails transiently (store the cut result instead of the 429) is a separate design choice for the controller.

## Budget accounting with the re-ask

- **Per-pass cost.** The gate (`sidecar:132`) admits a pass when `used + todo.length ≤ 18`. With the re-ask, a pass can cost up to `2 × todo.length`. Real requests per model are therefore ≤ 18 + (cuts in the last admitted pass) + (N2 events).
  - Anything past 20 is a server 429.
  - Tier 1 attempts at most 20 + N2 events.
  - Tier 2 attempts at most 21 + N2 events (a third cut in its last pass is the 21st request).
  - Tiers 3 and 3b have more room: up to 11 cuts in pass 1, or up to 7 in a later pass that starts at `used` = 11. In both cases the excess past 20 is refused by the server.
- **Accepted by the ruling** ("worst case a cut on every id of tier 3 exceeds 18 by the cuts, capped by the 20/day 429").
- **Consequences:**
  - The console can print "19/18" or "20/18 requests used".
  - The original report's self-review line "Budget can never be exceeded" (task-4-report.md:102) is no longer true, and the fix round did not revise it.
  - The only accounting *defect* is N2.
