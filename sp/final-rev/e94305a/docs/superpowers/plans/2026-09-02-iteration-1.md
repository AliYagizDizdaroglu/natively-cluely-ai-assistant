# Iteration 1 — the after-run's answers were quota-walled

**Run:** `auto after`, 2026-09-03 04:10:24 → ~05:11 UTC (working tree at 831bfb5 + the user's uncommitted work; STT = Groq REST).

## Symptom
The hour's detection side worked (mid-run at 27 min: 32 in-hour answer dispatches, 0 chips, 26 duplicate drops, 1 scenario merge, 7 coding-advisory overrides, 0 negotiation classifications, 0 socket closes), but nearly every answer stream failed: since 04:09, 36 `generateStream invoked`, 35 `verbal primary FAILED pre-token`, 34 `generateStream FAILED (fallback exhausted or unavailable)`, 2 `answer head` lines (one primary at 04:10:17, one fallback at 04:15:26). The first `[WhatToAnswerLLM] Stream failed` came at 04:09:55 — the first answer after the probe.

## Evidence
- `natively_debug.log`: 33 × `[ERROR] [WhatToAnswerLLM] Stream failed: ApiError … "code": 429 … "You exceeded your current quota"`; the bodies carry `quotaMetric: generativelanguage.googleapis.com/generate_content_free_tier_requests`, `quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier`, `quotaValue: 500`, `retryDelay: 16s–49s`. Models named: gemini-3.1-flash-lite (selected), gemini-3.5-flash-lite (fallback), a few gemini-3.1-pro-preview / gemini-3.8-flash.
- `interview60.auto.log`: `PROBE gemini-3.1-flash-lite HTTP 200` at 04:09:40, preflight READY at 04:09:42 — fifteen seconds before the first 429.
- Earlier the same key returned 429 to the same probe at 02:36 UTC.

## Root cause
The Gemini free tier allows 500 generate requests per model per day; the quota day resets at midnight Pacific (07:00 UTC). The before-run (2026-09-02 15:47 UTC), its answers and chains passes, and everything since all fall in the same quota day, so both the selected model and the fallback were exhausted before the hour started. The harness's probe is one `generateContent` with `maxOutputTokens: 1`; after a long idle period the limiter lets one or two requests through even when the day's quota is spent (the 200 at 04:09:40, then 429s), so a single 200 proves nothing about the hour.

Secondary: `computeRun` counted every `[Main] dispatch: answer` as an answer; nothing checked that the stream produced text. In the before-run every dispatched answer succeeded, so the gap was invisible.

## Fix (this iteration)
1. Probe hardening (`interview60.run.mjs`): READY requires five consecutive `generateContent` 200s, 15 s apart, on the primary model (one attempt logged per line); one 429 restarts the count. A walled key cannot pass this.
2. Delivered answers (`interview60.metrics.mjs` + test + report): `answerFailures` = `[WhatToAnswerLLM] Stream failed` lines in the run window; `delivered = answered − answerFailures`; the "Answered hands-free" gate row is judged on `delivered` and shows `delivered/dispatched`.
3. Re-run the hour after the reset (`auto after2`, launched with the hardened probe and a deadline past 07:00 UTC); run the answers and chains passes on it; the comparison page uses run 2. Run 1's snapshot is kept for its detection rows.

## What run 1 still proves
Dedup across detectors (whisper-first and Live-first both drop the duplicate with `answered=true`), the coding-advisory override, the whole-word classifier (0 negotiation), the scenario merge, and Live-mode restore on autostart — all independent of the answer's success.
