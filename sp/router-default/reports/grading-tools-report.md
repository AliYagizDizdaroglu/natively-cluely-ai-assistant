## How the controller runs it
1. Reader: nothing to run by hand any more (fix I-2): the scorer spawns `router-hour-read.mjs <run> --down-limit-min 2 --root <MAIN>` itself and prints the reader script sha, the reader output sha and the run folder.
2. Blind export: `build-blind-rd.mjs` (existing), then the exports `interview60.judge.mjs <run> --export` and the three arm exports.
3. Launcher, in this order (all `--model-id claude-opus-5-5` except the alias probe):
   - `node launch-grader-rd.mjs cwdprobe-1 --probe --model-id claude-opus-5-5`, then `cwdprobe-2` (same), then `cwdprobe-3 --probe` (the alias read, reported only);
   - `node launch-grader-rd.mjs --plan --run-dir <run>` (read-only; lists every launch; exit 3 on a blocker);
   - each tag: `blind-N.g1|g2`, `inapp.g1|g2`, `high`, `low`, `captured-high`, with `--run-dir <run> --model-id claude-opus-5-5` (add `--dry-run` first if wanted). Graders per file: blind 2, in-app 2, high 1, low 1, captured-high 1 (registration 7.2). Verdicts land in `LAB\grade\verdicts\verdicts.<tag>.json`, launch records in `LAB\grade\launches.jsonl`, grader cwds in `LAB\grade\grading\<tag>-a<k>`.
4. Scorer: `node score-rd.mjs --run-dir <run> [--grade-dir LAB\grade] [--key-dir LAB\keyhold] [--root <MAIN>]`. Exit 0 = scored (read the `VERDICT` line), exit 2 = refused. It also writes `LAB\grade\score-rd.out.txt` (counts and ids only).

## What the scorer does (every rule is the registration's)
- Inputs: the reader's stdout (the scorer runs the reader itself), `key-rd.json` + `build-record-rd.json`, the blind pairs files and verdicts (2 graders per file), the in-app export and verdicts (2 graders), the run's log, the roster. Optional reported-only arms (one grader).
- Refuses (exit 2): folder name not `<stamp>-router-default-r1`; reader output with a missing line or a flag that disagrees with its own numbers or with the registered thresholds; build record for another run; live/shadow capture file, roster or judge file whose sha256 differs from the build record (registration 7.7); missing key/record/in-app export/log/timeline; log not covering the hour or restarted inside it; blind pairs file and key disagreeing; a corrupt key (two Live or two S entries for a turn, an S with no Live entry).
- A gating verdict file that is missing, invalid, from a launch whose LAST record is not exit 0 / slugJsonl 1 / memory ABSENT / pinned, or whose two graders share a session, is dropped and printed as `GRADING PROBLEM`; its bars read UNREADABLE and the verdict cannot be PASS. A Safety FAIL on data that can be read still stands. A problem in a reported-only arm is printed and gates nothing.
- Bars as registered: Safety (reader text half clean AND no key entry with arm L, any class, graded wrong), Fallback/Speed/Routing (reader numbers re-applied: p50 <= 2500 with n > 0; EASY caught >= 13; HARD misrouted <= 1), Quality (L >= S - 1 over eligible pairs, paired by TURN, `['S','A']` counts as S, sEmpty/superseded/no-pipeline excluded and printed), No regression (HARD only: in-app on `shown=pipeline` turns joined by the `[Router] dispatch` line, plus every entry with arm A, plus superseded replacing texts), Integrity (nine reader counts).
- Verdict order: VOID, SAFETY FAIL, PASS (all six bars, integrity 0, no grading problem), else INCONCLUSIVE. Output never carries an answer, a question or the key's map; it prints roster ids and turn numbers of wrong answers.

## Places the registration was ambiguous (decisions made, each easy to flip; please rule)
1. **RULED: keep the stricter reading (either grader).** Was: **"consensus-wrong" vs "either grader".** Sections 5 and 7.2 say Live answers must not be "consensus-wrong"; the grade definitions (7.1, SPEC 10) say wrong = EITHER grader gives correctness 0. I applied the definition (stricter). If "consensus" was meant (both graders), `isWrong` flips to `&&`.
2. **Two graders disagreeing.** The registration has no adjudication rule beyond the asymmetric definitions, and I invented none: acceptable needs both at 2/2, wrong needs either at correctness 0 (g1 acceptable + g2 weak = not acceptable, not wrong; g1 acceptable + g2 correctness 0 = wrong). One grader's 0 settles "wrong" even when the other grade is missing (my reading of "either"); every other bar needs both grades.
3. **The I-2 join is unspecified.** Implemented as: the pair's `dispatchedAt` equals the timestamp of exactly one `[Main] dispatch: answer` line, and its turn is the first `[Router] dispatch turn=` line at or after it and before the next answer line (verified against the real judge's pairing). Anything else is a join defect: unreadable if the item is HARD.
4. **Superseded replacing text (7.3) probably cannot be satisfied by the in-app export as built.** The judge claims for an answer dispatch only the first `[Answer] full:` after it (plus later lines for a MAIN extend/supersede dispatch). The replacing line of an arbiter-level supersede (`[Router] superseded`, no main supersede dispatch) is claimed by nobody, so it is not in the export, so there is nothing to grade. My scorer then reads the HARD superseded turn as UNREADABLE (INCONCLUSIVE), never as a pass. Unless the smoke shows the text is in the export (registration 7.3 says pass 2 confirms), any HARD supersede forces INCONCLUSIVE. A fix needs an amendment (a small extra export of those texts). I also chose the window (first `[Answer] full:` line after the superseded line and before the next turn's dispatch) and: an unknown item for a superseded turn counts as unreadable.
5. **Zero eligible Quality pairs** reads as not met (UNREADABLE), not a vacuous PASS; **an ungraded side of a pair** makes Quality UNREADABLE rather than dropping the pair.
6. **RULED by the coordinator (implemented): a `shown=pipeline` turn with no in-app pair** caps the verdict at INCONCLUSIVE when its item is HARD or cannot be mapped (item from the play window, the reader's rule); on an EASY item it is a WARNING only. 7. **Reported-only arms** (`high`, `low`, `captured-high`): one grader, so acceptable/wrong are applied to that one grader's scores; counted over the file's items (31 mains for high/low).
